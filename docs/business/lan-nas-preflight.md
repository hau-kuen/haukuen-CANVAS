## 2. 实测明细

### 2.1 端口矩阵

| 端口 | 服务 | 状态 |
| --- | --- | --- |
| 5000 | DSM HTTP | OPEN |
| 5001 | DSM HTTPS | OPEN |
| 445 | SMB | OPEN |
| 139 | NetBIOS | OPEN |
| 80 / 443 | Web Station / 反向代理 | OPEN |
| 5005 / 5006 | WebDAV / WebDAV HTTPS | closed |
| 6690 | Synology Drive | closed |
| 22 | SSH | closed |

### 2.2 TLS

- 协议：TLS 1.2
- 证书：自签，`O=Synology Inc., CN=synology`，签发者 `Synology Inc. CA`
- 影响：后端若走 HTTPS API 需忽略证书校验；走 SMB 挂载则无此问题

### 2.3 SMB 协商结果

```
方言     : SMB 3.0.2
状态     : 0x0（成功）
签名模式 : 1（启用，非强制）
SMB3加密 : 不支持
```

解读：
- Windows 直接 `net use` 挂载没问题。
- 无传输加密，局域网内可接受；若以后要跨网访问，必须走 VPN。
- **不支持 SMB3 加密是 ARM 机型的典型特征**（无 AES-NI 硬件加速，群晖不给该选项），这是下面型号判断的依据之一。

### 2.4 网络状态

| 项 | 值 |
| --- | --- |
| 主机以太网 | `169.254.223.70/16`（APIPA，DHCP 未获取到地址） |
| NAS IPv6 | `fe80::211:32ff:fedf:622b`（EUI-64，由 MAC 推导） |
| TCP 连接延迟 | 15~25 ms（首次），后续 0 ms |
| 协商速率 | 100 Mbps / 全双工 |
| mDNS 历史缓存 | `diskstation.local → 192.168.2.200`（说明 NAS 曾配置过该静态地址） |

**为什么 IPv4 不通**：直连时链路上没有 DHCP 服务器，主机和 NAS 都退回链路本地地址；NAS 的 IPv4 要么是 APIPA、要么保留着旧的 `192.168.2.200`，两者都与主机的 `169.254.x` 不同网段。

**为什么速率只有 100M**：千兆口协商到百兆，只有三种可能——网线是 4 芯（超五类以下 / 断芯）、两端有一端是百兆口、水晶头压制不良。**这条线跑 NAS 会严重拖慢大图与视频传输**（100M ≈ 11 MB/s，1G ≈ 110 MB/s）。

---

## 3. 型号判断：大概率是 DS220j

三条独立证据：

1. 协商结果停在 **SMB 3.0.2 且无 SMB3 加密**。DS220+ 是 Intel J4025，支持 AES-NI，群晖会开放 SMB3 加密与 SMB 3.1.1。
2. 设备在直连下未启用任何需要 x86 的套件服务，Drive / WebDAV 均未安装（新机默认状态）。
3. DS220 系列只有 j 与 + 两个版本，j 为 ARM RTD1296 + 512MB。

**如确认是 DS220j，直接决定三件事：**

| 影响项 | 结论 |
| --- | --- |
| 后端能否跑在 NAS 上 | ❌ 不能。DS220j 不支持 Docker / Container Manager，后端继续留在这台 Windows |
| 能否用 Btrfs 快照做工程版本回溯 | ❌ 不能。DS220j 只有 ext4，备份靠 Hyper Backup 定时任务 |
| WebDAV 性能 | 弱。ARM + 512MB，小文件写放大明显 → **更坚定走 SMB 挂载方案** |

> 请在机器正面/底部标签上确认型号，或在 DSM「控制面板 → 信息中心」查看。

## 4. 上线前配置清单（需要在 DSM 里操作）

按顺序做，前 3 步做完我就能接管后续所有技术配置。

### 第 1 步：把 NAS 接回路由器（关键）

直连方案无法支持第二台电脑，与"多人共享"目标冲突。请把 NAS 网线插到你现在 WiFi 用的那台路由器（网关 `192.168.1.1`），并在路由器里给它做 **DHCP 静态绑定**（固定 IP，例如 `192.168.1.200`）。

> 顺手换一根超五类（Cat5e）以上、八芯完好的网线，目标协商到 1000 Mbps。

### 第 2 步：DSM 内建目录与账号

| 操作路径 | 内容 |
| --- | --- |
| 控制面板 → 共享文件夹 → 新增 | 名称 `canvas`；**开启回收站**；权限只给下面创建的账号 |
| 控制面板 → 用户与群组 → 新增 | 用户名 `canvas`；普通用户；只勾 `canvas` 文件夹的读写；**不要给管理员权限** |
| 控制面板 → 文件服务 → SMB | 启用 SMB 服务；最低协议 SMB2；最大 SMB3；传输加密保持关闭（硬件不支持） |
| 控制面板 → 硬件与电源 → 硬盘休眠 | 设为「无」，避免首访问 3~5 秒抖动 |
| 存储管理器 | 记录 RAID 类型与总可用容量，写进配置文档 |

### 第 3 步：确认存储规划

- 4TB × 2 做 SHR/RAID1 时可用约 3.6TB；建议给 `canvas` 设配额（如 2TB），留出余量给 Hyper Backup。
- 装 **Hyper Backup**，把 `canvas` 每日备份到外接硬盘或第二块盘（DS220j 无快照，这是唯一兜底）。

### 第 4 步（可选，我建议跳过）

不安装 WebDAV Server。按实测性能与硬件条件，**SMB 挂载 + 后端 local provider 是唯一合理路径**，WebDAV 作为跨网备用再说。

### 7.2 存储现状（关键）

| 卷 | 文件系统 | 总量 | 已用 | 剩余 |
| --- | --- | --- | --- | --- |
| volume_1 | ext4 | 7.93 TB | 7.76 TB | **170 GB** |

### 7.3 已生效的变更

| 项 | 变更前 | 变更后 |
| --- | --- | --- |
| SMB 最低协议 | SMB1 | **SMB2**（最高 SMB3，服务保持启用） |

### 7.4 未能通过 API 完成的操作

| 操作 | 结果 |
| --- | --- |
| 创建共享文件夹 `canvas` | `SYNO.Core.Share create` → **error 403** |
| 创建用户 `canvas` | `SYNO.Core.User create` → **error 3121** |

已穷举的尝试，全部一致拒绝：GET 与 POST 两种方式；HTTP 5000 与 HTTPS 5001；`FileStation` / `DSM` / `Core` 三种登录 session；SynoToken 放 query 参数与放 `X-SYNO-TOKEN` 请求头；参数最小化与 ASCII 描述。

## 8. 存储链路实测（2026-11-23，SMB 挂载闭环）

### 8.1 打通结果

| 项 | 结果 |
| --- | --- |
| NAS 管理 IP | `192.168.2.200`（静态，网关 `192.168.2.1`） |
| 主机直连口 | 加辅助 IP `192.168.2.10/24`（否则两边网段不通） |
| SMB 挂载 | ✅ `Z:` → `\\192.168.2.200\canvas`（账号 canvas） |
| 目录骨架 | ✅ `projects` / `uploads` / `generated` / `trash` / `_meta` |

**踩坑记录**：新建共享文件夹后 SMB 挂载报「系统错误 67 找不到网络名称」，根因是 samba 未重载新共享配置；通过重新 apply SMB 设置（`SYNO.Core.FileServ.SMB set`）触发重载后恢复。`net use` 用 PowerShell 传中文/带引号 UNC 会报语法错，改用 `cmd /c net use Z: \\host\share <密码> /user:<用户>`（密码紧跟共享路径）即可。

### 8.2 吞吐实测（512MB 顺序 + 200×20KB 小文件）

| 测试 | 结果 | 判定 |
| --- | --- | --- |
| 顺序写 512MB | **11.3 MB/s** | ⚠️ 百兆天花板 |
| 顺序读 512MB | **11.3 MB/s** | ⚠️ 百兆天花板 |
| 小文件（200×20KB） | 39 个/秒 | ⚠️ 偏慢 |

**结论：链路协商在 100 Mbps，不是千兆。** 11.3 MB/s 就是百兆的理论上限（100 Mbps ≈ 12.5 MB/s）。千兆应达 ~110 MB/s，当前慢了约 10 倍。

业务影响测算：
- 单张 50MB TIFF：存 4.5 秒、读 4.5 秒。
- 一场棚拍 500 张 × 50MB = 25GB：仅上传即需约 **40 分钟**，无法接受。

**根因与处理**（按概率排序）：
1. **网线是 4 芯**（百兆线），换 Cat5e 以上八芯线即可协商到 1Gbps —— 最可能。
2. 网卡/交换机口协商被限速（`以太网` 口曾显示 100 Mbps）。
3. 驱动节能降速。

> 这是本版本上线前的**硬阻塞**：多人共享时每人都会受这个 11 MB/s 限制，必须先把链路抬到千兆再谈生产。

### 8.3 换线后复测（千兆确认）

用户更换网线后，`以太网` 口协商到 **1 Gbps**，复测结果：

| 测试 | 结果 | 判定 |
| --- | --- | --- |
| 顺序写 512MB | **111.8 MB/s** | ✅ 千兆达标（约 10 倍于百兆） |
| 顺序读 512MB | **103.9 MB/s** | ✅ 千兆达标 |
| 小文件（200×20KB） | 72 个/秒 | ✅ 千兆合理水平（百兆为 39） |

**结论：链路阻塞已解决。** 业务测算更新：单张 50MB TIFF 存读各约 0.5 秒；一场棚拍 25GB 上传约 4 分钟（原 40 分钟）。

> `setup-nas.ps1` 的挂载语法已修正并实测通过：`& net use $Drive $unc $Password /user:$User /persistent:yes`（数组参数，密码紧跟共享路径）。原 `cmd /c "net use ... \"$unc\" ..."` 引号转义会报语法错。
